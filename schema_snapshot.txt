=====================================================================
This schema snapshot was rebuilt from live Postgres introspection
(information_schema + pg_catalog + pg_constraint + pg_enum against the
actual divya_drishti_ro grants), not from migration files. Migration
filenames in this project have repeatedly not matched the version
numbers stated inside the files themselves, so migration archaeology
is not a reliable source of truth - this file is. If a future schema
change needs reflecting here, re-run the four introspection queries
against the live DB rather than hand-editing from memory.

-- HR / ATTENDANCE ---------------------------------------------------------

analytics_leave_requests(id uuid pk, user_id uuid fk -> analytics_users.id, franchise_id uuid fk, from_date date, to_date date, leave_type text, status text, reviewed_by uuid fk -> analytics_users.id, reviewed_at timestamptz, created_at timestamptz)
  -- leave_type is one of: casual, sick, earned, unpaid. status is one of: pending, approved, rejected. Only status = 'approved' rows should count as actual days off when computing attendance/availability - a pending or rejected request is not a taken leave.
analytics_attendance(id uuid pk, user_id uuid fk -> analytics_users.id, franchise_id uuid fk, warehouse_id uuid fk, date date, check_in_at timestamptz, check_out_at timestamptz, status text, working_hours numeric, face_verified bool, is_within_geofence bool, created_at timestamptz)
  -- status is one of: present, absent, late, half_day, leave (plain text with a CHECK constraint, not a native enum - ILIKE works, but exact = is preferred). No row is ever created for a day someone didn't check in - a missed day is a MISSING row, not a row with status='absent'. Never compute attendance % as COUNT(attendance rows)/COUNT(attendance rows) - that is always 100%. Use this pattern instead, which generates every expected working day and LEFT JOINs actual attendance onto it so a missing day correctly counts against the person:

  WITH expected_days AS (
    SELECT u.id AS user_id, u.full_name, d::date AS work_date
    FROM analytics_users u
    CROSS JOIN generate_series(CURRENT_DATE - INTERVAL '1 month', CURRENT_DATE - INTERVAL '1 day', '1 day'::interval) AS d
    WHERE u.is_active = true AND EXTRACT(DOW FROM d) != 0  -- excludes Sundays; adjust to the actual work week if asked
  )
  SELECT ed.user_id, ed.full_name, COUNT(a.id) * 100.0 / COUNT(ed.work_date) AS attendance_percentage
  FROM expected_days ed
  LEFT JOIN analytics_attendance a ON a.user_id = ed.user_id AND a.date = ed.work_date
  GROUP BY ed.user_id, ed.full_name  -- group by user_id, not full_name alone: two different active
  -- employees can share the same full_name, and grouping by name alone silently merges their
  -- attendance into one blended, meaningless row.
  ORDER BY attendance_percentage ASC;

chat_conversations(id uuid pk, user_a uuid fk -> analytics_users.id, user_b uuid fk -> analytics_users.id, last_read_a timestamptz, last_read_b timestamptz, last_message_at timestamptz, last_message_preview text, created_at timestamptz, updated_at timestamptz)  -- one row per 1-to-1 internal staff conversation, not per direction. user_a is always whichever of the two user ids sorts smaller (user_a < user_b is a DB constraint) - it is NOT "who started the chat" and carries no meaning beyond sort order, so never describe user_a as the sender/initiator or user_b as the recipient. To name both participants, JOIN analytics_users twice (once on user_a, once on user_b). last_message_preview is a denormalized snippet kept in sync by a trigger purely for an inbox-list UI - for the actual message text, query chat_messages instead of trusting this field as complete.
chat_messages(id uuid pk, conversation_id uuid fk, sender_id uuid fk -> analytics_users.id, recipient_id uuid fk -> analytics_users.id, body text, attachment_path text, attachment_name text, attachment_mime text, attachment_size bigint, created_at timestamptz)  -- 1-to-1 internal staff direct messages. Permanent history: there is no edit or delete in this product, so every row that was ever sent still exists exactly as sent. body can be null when the message is attachment-only (every row has a non-empty body and/or an attachment, never neither) and is checked to be at most 4000 characters when present. attachment_path is a private Supabase Storage path, not a usable URL - don't present it as a link or guess at file contents from it; attachment_name/attachment_mime/attachment_size are the only attachment detail available. recipient_id is denormalized (it's always just "the other user in conversation_id") to support a realtime subscription filter - resolve both sender_id and recipient_id to analytics_users.full_name as usual, same as any other *_id column. "Unread" is not a column on either table - a given message counts as unread for a user when its created_at is later than that user's own last_read_a/last_read_b (whichever side of chat_conversations they are) on the parent conversation row.
  -- Private content: quote or summarize message body when the question specifically asks about a conversation or what someone said; don't volunteer it as incidental detail inside an unrelated broad query (e.g. a general activity/engagement overview should talk about message counts, not repeat what was said in them).

=====================================================================
NON-OBVIOUS FOREIGN KEYS AND RELATIONSHIP NOTES
(every *_by / *_to / *_id column above whose name doesn't obviously
name its target table, collected here so a join target is never
guessed. All targets that are PII-adjacent base tables are listed as
their analytics_* view, since that's what divya_drishti_ro can
actually query.)
=====================================================================

- Every *_by column (created_by, updated_by, raised_by, approved_by, resolved_by, recorded_by, received_by, performed_by, reviewed_by, generated_by, dispatched_by, assigned_by) points at analytics_users.id - it records a staff member, always resolve it to analytics_users.full_name.
- assigned_to / ai_recommended_to / to_user_id / from_user_id on leads and lead_assignments also point at analytics_users.id (a staff member being assigned work), not at a customer.
- team_leader_id on analytics_users is self-referential -> analytics_users.id.
- assigned_salesperson_id on analytics_customers -> analytics_users.id (account-level ownership - see the orders.lead_id vs this column distinction noted above).
- orders.delivery_address_id -> customer_addresses.id, a table NOT granted to divya_drishti_ro. This column exists but cannot be resolved - don't join it, say the address detail is unavailable if asked.
- orders.proforma_invoice_id and orders.gst_invoice_id both -> invoices.id. invoices.order_id is the same relationship from the other side - pick one direction, don't join both at once.
- products.po_item_id and skus.po_item_id both -> po_items.id (traces a catalog item back to the PO line it was received/created from).
- purchase_orders.purchase_invoice_id -> purchase_invoices.id is a direct link; purchase_invoices.po_id is the same relationship from the other side.
- inventory_movements.reference_id and notifications.entity_id are NOT fixed foreign keys - the target table varies by reference_type/entity_type on the same row, so don't attempt a blind join on either.
- dispatch_disputes (customer-facing, order-level) and analytics_po_disputes (vendor-facing, procurement-level) are two unrelated dispute workflows that happen to sound similar - don't merge them into one "disputes" concept without checking which one a question is actually about.
- analytics_payments (online gateway lifecycle: created/authorized/captured/failed/refunded) and analytics_order_payments (manually recorded offline payment: received/cleared/bounced) are two unrelated payment-tracking tables for the same order - check which one a "has this been paid" question actually needs; they are not interchangeable and a given order row may only exist in one of them.
- "Department" is not a concept this schema tracks - there is no departments table or column. If asked to break revenue/expenses/anything down "by department," map it to the closest real grouping this schema actually has (franchise, warehouse, or expenses.category) and say plainly which one you used, rather than inventing or guessing a column that doesn't exist.
